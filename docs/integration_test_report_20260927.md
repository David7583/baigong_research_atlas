## Harness真实接续

实际运行本机已安装的 `@deepseek-ai/dsh 0.1.5-rc.3`，无安装/下载。使用全新DSH_HOME、全新会话及合成文件，未复制客户端历史或登录凭据。仅启用文件工具，禁用子Agent、Shell、网络检索和遥测。

调用链：Harness → 带临时本机令牌的回环HTTP适配器 → 自身Action总控应用句柄 → DeepSeek。总控仍执行同步JSON；适配器在响应完整返回后发送SSE帧，不提供真正的实时流式推理，不自行调用Provider。最多8次请求，无自动重试。

初始单行JSON被客户端文件工具截断，模型误填project_id，校验拒绝归档。修改为多行JSON后，Harness完成read/read → write → final的真实工具循环（实际4次模型请求、22445 Token），正确继承项目/任务并保留反例与来源。宿主归档时发现错误能力枚举，修正为已有local_tools后直接恢复归档，不重发模型请求。

成果由宿主校验/归档，Harness没有直接写账本。当前Codex Agent再读取修订2、模型报告与证据，追加审阅修订3。原始失败记录保留；恢复证明单列，未改写原失败结果。

## 界面集成与实际交互

浏览器实际验证初始化、创建项目/任务、开始阶段、模型列表、启动/暂停、生成提案及显式归档。DeepSeek真实提案经界面生成并归档为修订1，保留call_id、Provider、模型和2979 Token的实际usage。暂停状态下生成被总控拒绝，不向模型发请求。

Kimi首次界面调用在120秒处返回provider_timeout，没有自动重试，没有推进任务修订。保留原任务后，仅隔离测试等待预算提高至240秒，进行一次显式恢复验证：真实请求在86.203秒完成，实际usage为5268 Token。该次成功不能证明延长超时是唯一原因，服务端延迟也可能变化。原主项目总控配置未修改。

Kimi提案在界面审阅后显式归档为修订2；project_id、task_id与DeepSeek阶段完全相同，两个run分别记录实际Provider和模型。刷新归档回执后修订仍为2，恢复测试总控仍只有一次请求。成功与超时证据分别保存在 `runtime/ui_live/d08e49e7/summary.json` 和 `runtime/ui_live/54e9338f/summary.json`，超时调用usage未知，不能按零费用计算。已停止全部本轮UI测试服务，并关闭隔离总控总许可及本应用许可。

内容审阅边界：Kimi正确区分原始合成观察与生成假设，承接了前阶段未决问题；但其“排除存在未纳入未决项的可能”表述超出当前快照可证明范围，且温度与事件时间同时变化，不能据此建立温度的因果效应。原生成成果完整保留。这是接续、来源与归档验收，不是模型结论准确率或真实科研质量验收。

修复了实际测试发现的问题：

- 模型能力兼容text_generation与chat，避免真实目录下拉框为空。
- 表单显式提交根路径，避免详情页查询参数触发请求拒绝。
- 成功/失败回执均使用POST后重定向，刷新不重复提交模型请求。
- 模型选择保留回显；错误后保留任务位置。
- 发送证据时保留作者、事件时间与来源哈希。
- 生成提案和正式归档分离；提案可重启后列出，页面中断不要求重新生成。
- 保留上一阶段未确认事项和未知操作，普通AI不能自动清除。
- 损坏交付包保留并报错，不阻断其他任务显示。
- 索引状态来自真实交付事件，不使用旧修订内的静态状态冒充实时状态。
- 暂停不等待正在进行的模型请求持锁；阻止下一次请求，但不虚称取消已经发送的请求。

已目视检查桌面布局及390px窄屏断点。窄屏DOM宽度390，scrollWidth375（含滚动条差），没有横向溢出；测试后恢复默认视口。
