# 跨语言脚本编写格式规范

版本：v0001  
状态：active  
格式母版：`scripts/action/anchor/sql_writer_v0004.py`

## 1. 目的

本规范从 `sql_writer_v0004.py` 的实际文件结构中提取一套语言无关的脚本编写格式，使 Python、PowerShell、Shell、Batch、JavaScript、TypeScript、Java、C、C++、C#、Go、Rust、SQL 等语言编写的脚本，都能以一致方式表达：

- 文件身份与版本；
- 主层级和职责边界；
- 输入、输出、依赖和调用关系；
- 配置与数据契约；
- 错误分类、审计和回退行为；
- CLI 接口、结构化输出和进程退出码；
- 可供 `scan_alias_meta` 提取的统一元数据。

本规范约束的是脚本的结构和可观察契约，不要求所有语言模仿 Python 语法。

## 2. 规范词

- **必须**：缺失即视为格式不合格。
- **应当**：通常必须遵守；只有明确记录理由时才可偏离。
- **可以**：按脚本职责选用。
- **不得**：禁止出现。

## 3. 适用边界

本规范适用于放入 `scripts/` 并需要被扫描、注册、调用、审计或长期维护的源代码入口。

以下对象不应仅因为与脚本相邻就登记为独立脚本：

- 图片、字体和音视频等静态资源；
- 纯样式文件；
- 自动生成且不作为独立入口的中间文件；
- 编译产物、缓存和第三方依赖副本。

如果 HTML、CSS 或 SQL 文件本身承担独立执行入口、迁移或查询职责，可以按本规范登记；否则应作为所属脚本的资源或依赖记录。

## 4. 注释包装规则

所有语言中的 Header 和 `ALIAS_META` 必须位于文件头部，并使用该语言合法的注释语法。扫描器在去除注释包装后，应得到本规范中的同一份规范化文本。

推荐的单行注释前缀：

| 语言或文件 | 前缀 |
|---|---|
| Python、PythonW、PowerShell、Shell、Ruby、Perl、R | `#` |
| JavaScript、TypeScript、Java、C、C++、C#、Go、Rust、Kotlin、Swift、Dart | `//` |
| SQL、Lua、Haskell | `--` |
| MATLAB、Octave | `%` |
| Visual Basic、VBScript | `'` |
| Batch、CMD | `REM `，大小写不敏感 |
| HTML、XML | `<!--` 与 `-->` 块注释 |

除 HTML/XML 等确有需要的格式外，应优先使用逐行注释，不应把 `ALIAS_META` 混入普通说明段落或字符串字面量。

## 5. 文件整体顺序

脚本必须按以下顺序组织。语言不支持某种语法时，使用该语言的等价实现，但不得改变职责顺序。

```text
1. 可选的解释器或编码声明
2. 文件说明 Header
3. ALIAS_META
4. 语言级导入 / 依赖声明
5. 全局常量与稳定标识
6. 错误类型
7. 输入输出数据结构
8. 无副作用工具函数
9. 默认映射与默认策略
10. 核心业务组件
11. 契约 / schema / 兼容性辅助函数
12. CLI 参数定义
13. main 调度与结构化输出
14. 语言级程序入口
```

不得把 CLI 解析、数据库连接、业务写入和入口调用无边界地混写在同一代码块中。

## 6. 文件说明 Header

### 6.1 固定顺序

Header 必须位于解释器声明之后、任何 import/include/use 之前，并按以下顺序书写：

```text
============================================================
文件名: <实际文件名，包含版本号和扩展名>
中文名: <简洁、可辨识的中文名称>
版本号: <v + 四位数字，例如 v0001>

主层级: <data | understand | action>
层级: <模块职责路径，例如 persistence / sql>
脚本定位: <一句话说明该脚本在系统中的位置>

职责说明:
- <职责 1>
- <职责 2>

本脚本做什么:
- <实际执行行为 1>
- <实际执行行为 2>

本脚本不做什么:
- <明确排除的职责 1>
- <明确排除的职责 2>

制度边界声明:
- <数据、事务、安全、调用边界 1>
- <数据、事务、安全、调用边界 2>

可更新: <True | False>
============================================================
```

### 6.2 字段要求

| 字段 | 要求 |
|---|---|
| 文件名 | 必须与磁盘上的真实文件名完全一致 |
| 中文名 | 必须描述职责，不得使用“新脚本”“最终版”等临时名称 |
| 版本号 | 必须与文件名和 `ALIAS_META.version` 一致 |
| 主层级 | 必须表达数据端、理解端或行动端归属 |
| 层级 | 必须表达模块职责，不得只重复主层级 |
| 脚本定位 | 必须说明它是入口、编排器、网关、写入器、校验器或其他角色 |
| 职责说明 | 必须描述稳定职责 |
| 本脚本做什么 | 必须描述真实实现，不写未来计划 |
| 本脚本不做什么 | 必须阻止职责扩张和错误调用 |
| 制度边界声明 | 必须记录数据安全、写入方式、事务或人工决策边界 |
| 可更新 | 必须明确能否继续演化 |

### 6.3 内容规则

- Header 描述必须与代码行为一致。
- 不得把尚未实现的行为写成已经具备的能力。
- 不得只写模糊表述，例如“处理数据”“执行任务”。
- 具有写操作的脚本必须说明写入目标、覆盖策略和失败行为。
- 涉及数据库的脚本必须说明是否建库、建表、迁移、写入、查询或校验。
- 涉及 AI 的脚本必须说明 Provider、模型和密钥由哪里提供，不得在 Header 中记录密钥值。

## 7. ALIAS_META

### 7.1 固定模板

`ALIAS_META` 必须紧跟文件说明 Header，字段名使用小写蛇形命名，并保持以下顺序：

```text
============================================================
ALIAS_META
============================================================
alias: <注册别名>
family: <脚本家族名，不含版本号>
role: <稳定角色名>
version: <v0001>
status: <active | deprecated | archived | experimental>
entry_point: <相对项目根目录的真实路径>
input:
  - <输入 1>
output:
  - <输出 1>
depends_on:
  - <依赖 1>
used_by:
  - <调用者 1>
============================================================
```

没有输入、输出、依赖或调用者时，也必须保留字段，使用空列表：

```text
input: []
output: []
depends_on: []
used_by: []
```

### 7.2 字段语义

| 字段 | 规则 |
|---|---|
| alias | 当前文件登记使用的真实别名；不得由扫描器猜测 |
| family | 文件家族名；同一家族多个版本必须相同 |
| role | 在调用链中的稳定职责，例如 `sql_write_gateway` |
| version | 与文件名及 Header 版本一致 |
| status | 表达当前生命周期状态 |
| entry_point | 使用项目根相对路径，不得写盘符、用户名或绝对路径 |
| input | 列出配置、CLI、标准输入、文件、数据库或调用参数 |
| output | 列出标准输出、文件、数据库、日志或状态变化 |
| depends_on | 列出运行所需脚本、标准库、第三方库、配置或外部服务 |
| used_by | 列出真实调用者；未来调用者必须明确标注 `future` |

样本 `sql_writer_v0004.py` 的 `alias` 自身包含版本号。跨语言脚本不得擅自删除或追加版本后缀；应按该家族已经采用的别名制度填写。`family` 和独立的 `version` 字段始终必须存在。

### 7.3 可扫描性要求

- `ALIAS_META` 必须出现在文件头部，不得放在函数、类、字符串或条件编译块内部。
- 一个文件只能有一个有效 `ALIAS_META`。
- 字段名必须使用 `[a-z_]+`。
- 列表项必须保持声明顺序。
- 文件必须使用 UTF-8；允许 UTF-8 BOM，但扫描器应规范化处理。
- 二进制文件不得伪装为可扫描脚本。

## 8. 文件命名与版本

版本化脚本使用：

```text
<family>_vNNNN.<extension>
```

示例：

```text
sql_writer_v0004.py
chat_ui_v0001.ts
start_chat_v0001.ps1
schema_loader_v0002.rs
```

要求：

- `NNNN` 必须为四位十进制数字。
- 文件名版本、Header 版本和 `ALIAS_META.version` 必须一致。
- 新版本不得使用 `final`、`new`、`fixed` 等替代版本号。
- 同一家族升级时保持 `family` 不变。
- 是否修改 `alias` 取决于该家族既有别名制度，不得在单个文件中自行改变规则。

## 9. 导入和依赖区

语言级 import/include/use/require 必须位于 `ALIAS_META` 之后、全局常量之前。

推荐顺序：

```text
1. 语言标准库
2. 第三方依赖
3. 项目内部模块
```

要求：

- 实际导入必须与 `depends_on` 相符。
- 可选依赖必须在代码中明确处理缺失路径。
- 不得静默切换到未声明的 Provider、SDK 或数据库驱动。
- 不得通过导入副作用执行正式业务写入。

## 10. 全局常量与稳定标识

脚本应在导入区后集中声明稳定常量，例如：

```text
DEFAULT_ENCODING
SCRIPT_FAMILY
SCRIPT_NAME
SCRIPT_VERSION
MAX_ROOT_SEARCH_DEPTH
路径或标识符校验规则
```

强制要求：

- `SCRIPT_FAMILY`、`SCRIPT_NAME`、`SCRIPT_VERSION` 必须与 Header/ALIAS_META 一致。
- 路径不得写死盘符、用户名或仓库绝对路径。
- 相对路径必须声明其解析基准，优先解析到项目根目录。
- 常量不得夹杂运行时可变状态。
- 密钥、Token 和密码不得作为源码常量。

## 11. 错误类型

复杂脚本应建立脚本级基础错误类型，再按职责细分。样本采用：

```text
SqlWriterError
├── ConfigError
├── SchemaError
├── PragmaError
├── DataError
└── IntegrityWriteError
```

跨语言要求：

- 必须区分配置错误、输入错误、契约错误和运行时/外部系统错误。
- 写入冲突不得只返回模糊的“失败”。
- 捕获错误时必须保留原错误类型和原因链，语言支持时使用 cause/wrap。
- 不得捕获后返回伪成功。
- 可恢复冲突与不可恢复错误必须使用不同状态或错误类型。

小型脚本如果不建立错误类，也必须输出等价的结构化 `error_type`。

## 12. 输入输出数据结构

核心输入、配置和返回结果应使用显式结构，而不是在代码各处传递无约束映射。

样本返回结构：

```text
WriteResult:
  status
  object
  object_id
  detail
```

样本配置结构：

```text
SqlWriterConfig:
  driver
  sqlite_path
  sqlite_timeout
  sqlite_pragmas
  tables
  fields
  runtime
```

跨语言可以使用 class、struct、record、interface、type、data class 或显式 schema 实现，但必须满足：

- 字段名称稳定；
- 必填和可选字段明确；
- 返回状态为有限集合；
- 序列化后的字段语义不因语言改变；
- 不得静默增加或改变公开字段含义。

## 13. 工具函数区

工具函数应放在核心业务之前，并尽可能无副作用。典型职责包括：

- UTC 时间生成；
- 内容哈希；
- 稳定 JSON 序列化；
- 输入类型和空值校验；
- 错误分类；
- 项目根目录发现；
- 配置标识符安全校验；
- 默认映射合并；
- 环境指纹；
- 稳定 ID 生成。

规则：

- 工具函数不得隐式执行正式写入。
- 时间统一使用带时区的 UTC 表达。
- 哈希算法、拼接顺序和编码必须固定并记录。
- 生成稳定 ID 时，参与计算的字段及顺序不得隐式变化。
- JSON 输出应保持稳定、可机读，不混入调试文本。

## 14. 默认映射与配置

可调参数必须优先放在配置文件中。源码默认值只能作为明确的兼容基线或安全兜底。

推荐顺序：

```text
1. 声明源码默认映射
2. 加载外部配置
3. 验证配置版本
4. 合并明确允许覆盖的字段
5. 校验必需组和必需键
6. 校验标识符与值域
7. 相对于项目根解析路径
8. 构造不可变或受控的配置对象
```

严格脚本必须在配置缺失、损坏、版本不匹配或字段不完整时返回明确错误，不得静默使用另一套 Provider、数据库或写入目标。

## 15. 核心业务组件

核心组件必须体现以下边界：

```text
构造 / 配置加载
    ↓
连接或外部资源准备
    ↓
运行前契约自检
    ↓
输入验证
    ↓
幂等性 / 依赖存在性检查
    ↓
dry-run 短路
    ↓
正式操作
    ↓
提交或成功返回
    ↓
失败回滚、错误分类、资源关闭
```

### 15.1 连接和自检

- 连接目标必须来自已验证配置或项目级固定约定。
- 建立连接后应验证必要运行参数。
- 对数据库、消息系统或外部服务的必需契约应在正式操作前检查。
- schema 不匹配时必须失败，不得擅自建表或迁移，除非该脚本明确就是 schema initializer。

### 15.2 输入验证

- 必填字符串必须拒绝空字符串。
- 布尔值不得被整数或字符串静默代替。
- 枚举字段必须验证值域。
- 内容哈希、稳定 ID 和引用关系必须在写入前校验。
- 类型转换失败必须返回输入错误，不得自动填入含糊默认值。

### 15.3 幂等性和追加式原则

- 必须明确区分 `inserted`、`existing`、`duplicate` 和 `error`。
- 原始事实和审计记录默认只追加。
- 不得因重复运行覆盖唯一事实。
- 更新操作仅在业务语义明确要求状态闭合时使用，例如关闭已存在的 run log。
- 删除或覆盖必须由专用脚本承担，并取得明确授权。

### 15.4 事务和资源释放

- 一次公开调用应有清晰的最小事务边界。
- 成功后显式提交。
- 任何异常都必须回滚。
- 连接、文件句柄、锁和临时资源必须在 finally/defer/RAII/using 等等价机制中释放。
- dry-run 必须验证输入与依赖，但不得执行正式写入。
- dry-run 不得创建数据库、目录或其他持久化对象，除非文档明确声明并获得授权。

## 16. 契约与 schema 辅助区

当核心组件依赖数据库 schema、索引、协议字段或其他稳定契约时，应在核心组件之后、CLI 之前集中声明契约辅助逻辑。

应检查：

- 必需表或资源是否存在；
- 必需字段及类型是否一致；
- 主键、非空约束和外键是否存在；
- 索引名称及列顺序是否一致；
- 类型兼容规则是否明确；
- 初始化器、配置和写入器是否使用同一套字段映射。

契约检查不得顺手修改 schema。发现不一致时，应指出正确的初始化或迁移入口。

## 17. CLI 接口

CLI 定义必须与核心业务分离，并位于文件尾部、`main` 之前。

### 17.1 全局参数

适用时应提供：

```text
--config
--dry-run
```

允许跳过安全检查的参数必须明确标记为不推荐，并默认关闭，例如：

```text
--no-verify-schema
```

### 17.2 子命令

一个文件承担多个紧密相关操作时，应使用子命令，而不是大量互斥布尔参数。

每个子命令必须：

- 有清晰动词名称；
- 明确必填与可选参数；
- 与一个核心公开操作对应；
- 保持参数名称和结构化输入字段的稳定映射。

### 17.3 标准输出

stdout 必须只输出机器可读的最终结果。推荐单行 JSON：

```json
{"status":"inserted","object":"concept","object_id":"...","detail":null}
```

错误输出也必须结构化：

```json
{"status":"error","error_type":"ConfigError","detail":"config not found"}
```

调试信息、进度和警告应写入 stderr 或正式日志，不得污染 stdout JSON。

### 17.4 退出码

样本采用以下分层，跨语言实现应保持等价语义：

| 退出码 | 语义 |
|---:|---|
| `0` | 成功，包括明确允许的 existing/duplicate 结果 |
| `2` | 已知、已分类的业务或契约错误 |
| `3` | 未分类的意外错误 |

如果语言或运行环境另有约定，可以扩展退出码，但必须在 Header 或 CLI 帮助中记录，不得让失败返回 `0`。

## 18. main 调度

`main` 只负责：

```text
1. 解析参数
2. 构造核心组件
3. 将 CLI 参数转换为核心接口参数
4. 调用一个明确操作
5. 输出结构化结果
6. 将错误分类映射为退出码
```

`main` 不应复制核心业务逻辑，不应直接拼装复杂 SQL，不应绕过配置和契约自检。

## 19. 程序入口

文件末尾必须存在该语言的显式程序入口，并把退出码交还给操作系统。

示例：

```python
if __name__ == "__main__":
    raise SystemExit(main())
```

```javascript
main().then(
  code => process.exit(code),
  error => {
    process.stderr.write(String(error));
    process.exit(3);
  }
);
```

```rust
fn main() {
    std::process::exit(run_main());
}
```

脚本被作为库导入时，不得自动执行 CLI 主流程。

## 20. 跨语言完整母版

下面的 `<C>` 表示目标语言的单行注释前缀。HTML/XML 应把对应区域包装在合法块注释中。

```text
<可选解释器声明>
<C> ============================================================
<C> 文件名: <family>_v0001.<ext>
<C> 中文名: <中文职责名>
<C> 版本号: v0001
<C>
<C> 主层级: action
<C> 层级: <module / responsibility>
<C> 脚本定位: <一句话定位>
<C>
<C> 职责说明:
<C> - <职责>
<C>
<C> 本脚本做什么:
<C> - <真实行为>
<C>
<C> 本脚本不做什么:
<C> - <明确边界>
<C>
<C> 制度边界声明:
<C> - <安全、数据、事务或调用约束>
```

## 21. 最低验收清单

新脚本进入 `scripts/` 前必须逐项确认：

### 身份和格式

- [ ] 文件名符合 `<family>_vNNNN.<extension>`。
- [ ] Header 文件名、版本号与磁盘文件一致。
- [ ] 主层级、层级和脚本定位明确。
- [ ] “做什么”和“不做什么”均已填写。
- [ ] 制度边界声明与真实实现一致。
- [ ] `ALIAS_META` 位于文件头部且只有一个。
- [ ] alias、family、role、version、status、entry_point 完整。
- [ ] input、output、depends_on、used_by 均存在。
- [ ] entry_point 是项目根相对路径。

### 实现结构

- [ ] 导入、常量、错误、数据结构、工具、核心逻辑、CLI、main 和入口分区清晰。
- [ ] 配置项没有散落硬编码。
- [ ] 没有盘符、用户名、绝对仓库路径或源码密钥。
- [ ] 输入在副作用发生前完成校验。
- [ ] 错误被分类且不会返回伪成功。
- [ ] dry-run 无持久化副作用。
- [ ] 写操作具有清晰事务和回滚边界。
- [ ] 文件、连接和锁能够可靠释放。
- [ ] stdout 输出可机读，诊断信息不污染结果。
- [ ] 非零失败退出码已定义。
- [ ] 作为模块导入时不会自动运行主流程。

### 注册和链路

- [ ] 文件扩展名已被 `scan_alias_meta` 支持。
- [ ] 该语言的注释格式已配置。
- [ ] 扫描结果能保留全部 ALIAS_META 字段。
- [ ] 依赖名称指向真实活动版本或稳定别名。
- [ ] used_by 与真实调用关系一致。
- [ ] 新版本已完成语法、最小功能、错误路径和前一版本行为对比。

## 23. 不从样本机械复制的内容

以下内容是 `sql_writer_v0004.py` 的业务实现，不是所有语言脚本都必须照搬：

- SQLite、PRAGMA 和 SQL schema 检查；
- Concept、Instance、Attribute 和 run log 字段；
- Python `dataclass`、类型注解和 `argparse`；
- Python 异常继承语法；
- SHA-256 作为所有业务 ID 的固定算法；
- `0/2/3` 之外不可扩展的退出码限制。

其他语言必须保留这些内容背后的结构职责：显式数据契约、输入验证、配置验证、错误分类、事务边界、结构化输出和可审计入口。

## 24. 最终原则

跨语言脚本不是只要“能够运行”就满足本项目格式。进入系统锚点的脚本必须同时做到：

```text
身份可识别
职责可理解
输入输出可对齐
依赖可追溯
错误可诊断
写入可回滚
结果可审计
入口可调用
版本可演化
```

语言可以不同，脚本在系统中的身份、边界和证据链不能不同。
